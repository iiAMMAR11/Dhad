# مخطط تجربة المستخدم لـ Dhad

## 1. المستخدم والسياق

النظام مبني أصلًا لمجموعتين:

1. فريق إنتاج محترف: مدير إنتاج، مصور، مساعد إخراج ومونتير.
2. صانع محتوى منفرد يدير الكتابة والتصوير والمتابعة وحده.

البيئة ليست مكتبًا هادئًا. الاستخدام يحدث أثناء الحركة، تحت ضغط وقت، في إضاءة متغيرة، وعلى هاتف بيد واحدة. لذلك القرارات الأساسية في النظام هي:

- الوصول للفعل خلال لمسة أو اثنتين.
- منع فقدان العمل مع save/sync feedback.
- كثافة معلومات مفيدة بلا زينة.
- إبقاء الحالة الحالية واضحة دائمًا.
- دعم الجوال كواجهة كاملة، لا نسخة ناقصة من سطح المكتب.

## 3. نموذج التنقل

### المستوى الأول

الرئيسية تجمع طرق عرض متعددة لنفس الكيانات:

- Files: ترتيب هرمي بالملفات.
- List: مسح سريع وكثافة أكبر.
- Kanban: حالة إنتاجية عبر كتابة، جاهز، تحرير، تم.

هذا قرار UX مهم: لا تُنشئ بيانات منفصلة لكل view. الثلاثة projections لنفس المصدر، ويُحفظ آخر view محليًا.

### المستوى الثاني

فتح مشروع ينقل إلى مساحة عمل مركزة. معلومات المشروع قابلة للطي لتوفير الشاشة، وشريط الفلاتر والتقدم يبقى sticky.

### المستوى الثالث

المشهد والمقطع لهما fullscreen عند الحاجة للتركيز، لكن يمكن تعديل التفاصيل الأساسية inline لتقليل التنقل.

### لا توحّد عناصر الاختيار دلاليًا

قد تتشابه التبويبات والاختيارات المقسمة ومبدلات العرض بصريًا، لكنها ليست مكوّنًا سلوكيًا واحدًا:

- route navigation: روابط مع `aria-current` عندما يتغير المسار.
- tabs: `tablist/tab/tabpanel` مع roving tabindex والأسهم وفق اتجاه الواجهة.
- segmented radio: `fieldset` و`legend` وradio group لاختيار قيمة واحدة داخل نموذج.
- view toggle: أزرار مضغوطة بـ`aria-pressed` عندما يتغير projection لنفس البيانات.

لا تستخدم filter chips أو success checkboxes كبديل سريع لأي من هذه العقود.

## 4. التدفّقات الرئيسية

### 4.1 الدخول والتسجيل

1. عرض سبب الدخول: المزامنة على الأجهزة.
2. username + password.
3. إظهار/إخفاء كلمة المرور.
4. تبديل الدخول/التسجيل في نفس البطاقة.
5. عند التسجيل تظهر تحذيرات الخصوصية والأمان.
6. loading ثم success/error واضح.

معيار التعميم: اشرح قيمة المصادقة قبل طلب البيانات، ولا تعرض التحذيرات الطويلة خارج اللحظة المناسبة.

### 4.2 إنشاء مشروع

1. المستخدم يضغط «جديد».
2. يختار تصويرًا أو ملفًا.
3. prompt مخصص للاسم.
4. يظهر الكيان فورًا في الواجهة.
5. يحفظ محليًا ثم يزامن، مع save state.

المبدأ: optimistic UI مع إشارة فشل لا تختفي حتى نجاح كتابة لاحقة.

### 4.3 تجهيز التصوير

1. فتح معلومات المشروع.
2. إضافة مهام منفردة أو لصق عدة مهام تفصلها أسطر.
3. تحديد المكتمل.
4. progress نصي وبصري.
5. المهمة المكتملة تبقى ظاهرة مع strike حتى يظل السياق محفوظًا.

### 4.4 كتابة المقاطع والمشاهد

يوجد مساران مكملان:

- Structured UI: إضافة مقطع ثم مشاهد وحقول.
- Minimal writer: كتابة `#` لمقطع و`##` لمشهد، مع إحصاءات فورية.

المبدأ القابل لإعادة الاستخدام: وفر واجهة بنيوية للمستخدم الدقيق وواجهة إدخال سريعة للمستخدم الذي يريد التدفق، لكن اجعلهما يحرران النموذج نفسه.

### 4.5 يوم التصوير

1. فتح المشروع.
2. filter حسب المنجز/المعلق والوجه والركن.
3. فتح المشهد fullscreen.
4. قراءة المحتوى أو تشغيل teleprompter.
5. بدء مؤقت التايم كود.
6. إضافة ملاحظات أثناء التسجيل بلمسة واحدة.
7. تحديد المشهد منجزًا.
8. التقدم يتحدث دون مغادرة السياق.

### 4.6 teleprompter

1. تحميل النص المنسق بعد sanitization.
2. تحديد الحجم والسرعة.
3. فتح نافذة ثانية عند استخدام شاشة مرآة.
4. mirror on/off.
5. play/pause/reset/manual scroll.
6. مزامنة الموضع بين شاشة التحكم وشاشة العرض عبر BroadcastChannel.

### 4.7 التصدير

1. يختار المستخدم الصيغة.
2. validation للبيانات المطلوبة.
3. بناء الملف client-side متى أمكن.
4. نجاح: download أو فتح Final Cut عبر helper محلي.
5. فشل: toast يشرح السبب والإجراء التالي.

## 5. قواعد التفاعل

### سرعة الفعل

- التعديل inline قبل فتح modal.
- Enter يعتمد الإدخال عندما يكون ذلك متوقعًا.
- paste متعدد الأسطر يحول النص إلى عناصر متعددة.
- actions النادرة داخل menu؛ الأفعال اليومية ظاهرة.
- حفظ تلقائي بدل زر حفظ متكرر، مع dot حالة يمكن تفسيره بالنقر.
- الإدخال السريع يعلن افتراضاته قبل التنفيذ، مثل القيمة الافتراضية أو الأشخاص المشمولين، ويظل له مسار واضح لفتح النموذج الكامل.

### الرجوع والتراجع

- حذف المشروع soft delete إلى trash.
- حذف الملف لا يحذف المشاريع داخله؛ يفك الارتباط.
- القرارات destructive تمر عبر confirm مخصص.
- Escape والخلفية يغلقان sheets غير الحرجة.

### السحب والترتيب

- drag handles منفصلة عن فتح البطاقة.
- drag-over يغير الحد بوضوح.
- يجب توفير طريق بديل عبر القائمة لتغيير الحالة أو الترتيب.
- على الجوال لا يعتمد النظام على hover.

## 6. نموذج الحالة والتغذية الراجعة

| الحالة | اللون | النص/السلوك |
|---|---|---|
| idle | border | لا رسالة |
| saving/syncing | accent | جارٍ الحفظ/المزامنة |
| saved/synced | success | آخر حفظ + وقت عند النقر |
| failed | danger | يبقى حتى نجاح لاحق، لا يختفي صامتًا |
| offline | text-3 | يوضح أن العمل محلي |
| destructive | danger | تسمية فعل صريحة مثل «حذف» |
| complete | success | علامة + نص + تقدم |

أنماط feedback:

- inline validation للمشكلة القريبة من الحقل.
- toast لنتيجة عملية عابرة.
- persistent indicator لحالة المزامنة.
- bottom sheet لقرار قصير يتطلب اختيارًا.
- inset أو full-height task-form dialog لإدخال طويل متعدد الأقسام يحتاج تمريرًا داخليًا أو لوحة مفاتيح أو فعلًا ثابتًا.
- empty state لغياب المحتوى، لا لفشل الشبكة.

## 7. استراتيجية الجوال

ضاد mobile-first في السلوك حتى لو كانت بعض layouts تبدأ من سطح المكتب:

- safe-area في topbar، overlays والجزء السفلي.
- حقول 16px عند الحاجة لمنع iOS zoom.
- أهداف اللمس 44px.
- bottom sheets للقرارات القصيرة. لا تحوّل كل حوار تلقائيًا: نموذج المهمة الطويل يمكن أن يبقى inset أو ينتقل إلى full-height مع رأس وفعل سفلي ثابتين.
- action rows تلتف بدل تقليص النص.
- dropdown actions المهمة تظل ظاهرة لأن hover غير موجود.
- أعمدة desktop تتحول إلى stack.
- زوج حقول قصير ومترابط، مثل مبلغ وتاريخ، يمكن أن يبقى في صف واحد ما دام كل حقل صالحًا للمس والتكبير ولا يقتطع العربية. يتحول إلى stack عند 320px أو مع Dynamic Type الكبير.
- كانبان يبقى أفقيًا مع snap لأن تحويله لقائمة يفقد معنى المرحلة.
- teleprompter لا يعرض فعل النافذة الثانية على الهاتف عندما لا يكون use case منطقيًا.

## 8. استراتيجية سطح المكتب

- max-width يمنع تمدد القراءة والحقول.
- hover يكشف الأفعال الثانوية مع بقاء الوصول عبر focus-within.
- fullscreen يستعمل عمودين: حقول + timecode/reader.
- modals وسط الشاشة بعرض محدود.
- kanban يعرض أربع مراحل متوازية.
- editor يبقى بعرض قراءة، لا يتمدد مع الشاشة.

## 8.1 البيانات الكثيفة على الهاتف

- استخدم ledger row عندما يحتاج كل سجل وصفًا وmetadata وقيمة مقابلة. احجز عمود القيمة كي لا تدفع العناوين الطويلة الأرقام إلى مواضع مختلفة.
- اجمع الصفوف المرتبطة داخل list group واحد. لا تحوّل كل سجل إلى بطاقة منفصلة بلا حاجة.
- المبلغ الأساسي أقوى بصريًا؛ التحويل التقريبي والحصة الشخصية معلومات ثانوية معلّمة بوضوح.
- summary grid يحافظ على محاذاة الأدوار المتوازية. طول تسمية في خلية لا يغيّر موضع القيمة أو الفعل في الخلايا الأخرى.
- المخطط المصغر ليس progress. وفّر وصفًا نصيًا للاستنتاج، وقيمًا متاحة لقارئ الشاشة، وحالة صريحة لغياب البيانات.

## 9. المشاركة والتعاون

التطبيق يدعم:

- مشاركة مشروع عبر رابط capability.
- أدوار owner/editor/viewer.
- أعضاء وavatars.
- view-only banner.
- دردشة على مستوى المقطع.
- sync عبر Firestore وoffline persistence.

قواعد UX القابلة للتعميم:

- اعرض الدور الحالي دائمًا إذا كان يقيّد الأفعال.
- اخف/عطّل أفعال الكتابة في view-only، ولا تنتظر فشل الخادم.
- إلغاء الرابط أو العضو فعل destructive مستقل.
- حالة sync منفصلة عن حالة الحفظ المحلي.

## 10. PWA والعمل دون اتصال

- manifest عربي وRTL.
- standalone display.
- portrait-primary.
- service worker caching.
- localStorage كطبقة محلية سريعة مع Firestore للمزامنة.
- sync state يفرق بين synced وoffline وfailed.

للمشاريع الجديدة يجب تحديد source of truth بوضوح. لا تخلط optimistic local state مع cloud state من دون conflict policy وإشعار للمستخدم.

## 11. سهولة الوصول

### ما يعمل جيدًا

- RTL وlang من الجذر.
- skip link.
- focus ring عام.
- reduced motion.
- أزرار رمزية تحمل labels في أغلب المواضع.
- 44px touch targets في الجوال.
- الحالات لها نصوص وأرقام بجانب اللون.

### ما يحتاج تعزيزًا قبل التعميم

- focus trap للحوارات المعقدة.
- بديل keyboard كامل للسحب.
- اختبار contrast الفعلي للـ alpha surfaces.
- جعل الإيموجي اختياريًا ومتكيّفًا مع لغة المنتج، مع أسماء متاحة للرموز التفاعلية وعدم الاعتماد على شكلها وحده.
- مراجعة النصوص 11px.
- إعلان تحديثات sync المهمة عبر aria-live.
- اختبار VoiceOver بالعربية وترتيب DOM مقابل الترتيب البصري RTL.
- اختبار تنقل الأسهم في tabs وsegmented controls، وعدم ربط checkbox الاختيار بلون النجاح.
- قراءة المال والعلاقات الاتجاهية كنص مفهوم، لا كسلسلة رموز أو سهم منفرد.

## 12. ما يجعل تجربة إنتاج المحتوى ناجحة

- تختصر domain model الحقيقي: تصوير ← مقاطع ← مشاهد.
- تربط الكتابة والتصوير والمونتاج في سلسلة واحدة.
- teleprompter وtimecode ليسا إضافات شكلية؛ هما جزء من المهمة الميدانية.
- Final Cut export يغلق الحلقة من التخطيط إلى المونتاج.
- نفس البيانات تظهر كملفات، قائمة وكانبان بحسب سؤال المستخدم الحالي.
- واجهة عربية أصلية في النص والترتيب والاختصارات.

## 13. ما لا يجب نسخه حرفيًا لكل مشروع

- مفردات التصوير وأيقوناته.
- أربع مراحل كانبان نفسها.
- Firebase كاختيار تقني ثابت.
- قاموس إيموجي من منتج آخر أو أي قاموس ثابت بوصفه حلًا دائمًا للهوية.
- كل modal أو sheet بلا سؤال: هل السياق يحتاجه؟
- كل hardcoded inline style من الملف الأصلي.
- الخط التجاري من دون ترخيص.

## 14. خطة الاعتماد في مشاريع متعددة

### المرحلة 1: Foundation

- استيراد tokens وbase components.
- إضافة ملفات الخط المرخصة أو اختيار بديل معتمد.
- تثبيت dark/light policy.
- تفعيل focus، toast، sheet وminimum touch targets.

### المرحلة 2: Product mapping

- استبدال Project/Segment/Shot بكيانات المشروع الجديد.
- تعريف حالات workflow الخاصة به.
- تحديد الألوان الدلالية التي تبقى ثابتة والألوان الثانوية الخاصة بالمنتج.
- بناء IA وتدفّقات العمل قبل نقل أي layout.

### المرحلة 3: Domain recipes

- إنشاء مكوّنات فوق Core، لا داخلها.
- كل recipe يملك حالات loading/empty/error/offline/permission.
- المشاركون في حساب أو سير عمل ليسوا تلقائيًا أعضاء تعاون أو أصحاب صلاحيات. افصل النموذجين حتى لو تشابه صف العرض.
- اختبار الهاتف أولًا ثم سطح المكتب.

### المرحلة 4: QA

- keyboard + VoiceOver.
- 320px، 390px، 768px، 1024px و1440px.
- dark/light.
- reduced motion.
- offline/slow network/write failure.
- نص عربي طويل مع حركات وأرقام وروابط LTR.
- أسماء عربية ولاتينية مختلطة، عملات مختلفة الدقة، أرقام سالبة، تاريخ محلي وآلي، وتحويل تقريبي قديم أو غير متاح.
- touch targets وsafe-area.

بهذه الطريقة يبقى **Dhad** هوية مشتركة، من دون تحويل المنتجات إلى نسخ من مثال واحد.
